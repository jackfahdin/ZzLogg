# 文件追加后的搜索匹配计数修复

## 问题与原因

文件追加后，增量搜索会重新扫描上次的末行，以处理没有换行符的末行。旧实现没有维护 SearchData 的累计匹配成员集合，删除旧末行时也没有扣除其计数；重新匹配后再次累加，导致实际 3 条匹配显示为 4 条。

## 修复范围

- 接收搜索结果时维护累计匹配位图，独立于界面已经取走的增量结果。
- 重新扫描前，仅在实际删除旧匹配时扣减计数，同时清除尚未消费的对应结果。
- 重复删除不重复扣数，不改变搜索表达式或编码检测逻辑。

## 验证记录

- 修复前：真实文件追加回归测试得到 4 条，预期 3 条，测试失败。
- 修复前：待消费、已消费两组底层测试在删除后仍得到 2 条，预期 1 条，测试失败。
- 修复后：原已知失败用例移除 QEXPECT_FAIL，使用明确的 3 条匹配断言。
- 新增覆盖：结果待消费、结果已消费、重复删除、非匹配行删除、反复重扫以及清空状态。
- Windows Release 构建成功，CTest 60/60 通过。
- Windows 原生界面测试 46 项通过，0 项失败。
- 独立只读审查通过。

## 成本与未包含事项

累计成员集合额外保留一份 Roaring 压缩匹配位图，每批结果增加一次位图并集；本次没有进行专门的内存和性能基准测试。

审查另发现既有独立问题：未换行的末行追加内容后，如果从匹配变为不匹配，界面结果集合只做并集，可能保留旧结果。本次聚焦重复计数，不包含该结果移除问题。

本次在 codex/fix-tail-match-count 分支完成，不包含合并到 master 或推送。

## 2026-09-08 后续修复：移除失效的末行结果

用户确认继续修复上述独立问题后，新增真实文件追加回归：使用反向搜索，向未换行末行追加排除词。修复前界面计数已经变为 1，但结果列表仍为 2 行，严格断言失败。

后台现在同时传递新增和删除的匹配集合，并在同一把锁内取走两种增量。界面先删除旧匹配，再加入重扫结果；合并视图保留用户标记，不因搜索失效而删除标记。待消费的删除集合会在清空搜索时重置。
