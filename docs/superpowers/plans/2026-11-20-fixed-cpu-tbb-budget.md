# 固定 CPU 的 TBB 名额对照

> 使用 writing-plans／executing-plans 内联执行，最后一次新鲜上下文独立审查。

**目标与规格：** 延续 [调度诊断](2026-11-20-search-scheduling-diagnosis.md)，固定三个独立 P 核 CPU 0／2／4，只改变 TBB 全局上限 1／2／3。Qt／通知的配对结果、CPU、上下文切换和实际上限一起核对，区分名额变化与更换硬件的影响。不把上限当作实测活跃线程数。

**方案：** 显式 probe 和 runner 新增 `--tbb-limit`（1～256，省略保留自动值）。probe 在所有搜索／契约前建立 RAII global_control，覆盖索引、worker 和验证生命周期；每条计时与 profile 输出实际上限及默认并行度。runner 向每个子进程传递参数，逐条拒绝没有生效的结果，元数据记录请求值。只修改实验工具、测试和文档，生产 Qt／轮询不变，不加依赖或系统权限，不追加 Windows 验证。沿用本地 master 中文提交，不推送。

## 审查重点

- global_control 生命周期覆盖所有测量／后台 join，异常析构安全；上限不与匹配节点数混用。
- runner 的验证、计时、独立 profile 都收到相同参数；实际预算不符即失败，不能只记录请求值。
- 非整数、0、负数及超过 256 拒绝，省略参数仍兼容旧 probe；有限时的真实契约验证完整结果。
- 同二进制／同 CPU／同输入，名额组交错且保留全部样本，不用跨轮绝对时间作因果推断。
- 结论仍限于 Linux 合成日志，不把全局预算等同 CPU 使用率或具体锁耗时。

## 实现与验证

probe 的 `--tbb-limit` 使用局部 RAII `tbb::global_control`，在 fixture／搜索之前创建，所有 worker join 和异常栈展开完成后销毁。计时与独立 profile 的共同输出入口读取实际全局预算和 CPU 导出的默认并行度。runner 的统一子进程调用入口透传参数，包括 `--verify`；指定预算时，缺少实际值、类型不正确或实际值不等于请求值的行立即拒收。省略参数保留自动预算及旧 probe 兼容。

先运行新契约：真实旧 probe 以 `Unknown option 'tbb-limit'` 失败，Python 缺少预算校验函数。实现后，memchr／PCRE 两构建都通过预算 1／2／3 × Qt／wake × 计时／profile 的完整结果检查；同时验证 runner 的记录和透传，拒绝 0、负数、非整数、超过 256 和溢出输入。每个预算的 runner 调用也执行原完整 `--verify`，包含取消、重搜与追加更新。

默认 `ci_build`、**99/99 CTest**、Python **148 项（3 项跳过）**和既有外部语料契约通过。生产 `src/`、Qt 匹配器、队列容量和调度默认值都没有修改。


### 独立审查修复

一次只读独立审查发现 Important：既有恢复契约按 CPU 导出的默认并行度判断并发能力。新增显式上限 1 后，机器仍可见多个 CPU，read／allocation 模式的握手超时会被误认为成功注入，原契约甚至返回 passed。

先增加“目标故障恰好注入一次”的断言，在三个独立 CPU、上限 1 的 read 模式观察退出码 1：`Requested recovery injection was not reached exactly once`。然后改为在实际 producer／matcher checkpoint 中检查 global_control 的生效预算和当前 arena 名额，单名额不等待不存在的并发回调。每个故障分支只在真正抛出预设异常前计数，等待超时不能冒充该计数。

真实预算契约扩展为 6 处故障 × 2 种调度 × 3 个预算，每个都验证全量失败、追加更新失败和同 worker 完整重搜。修复仅在实验工具内，没有更改生产错误处理。独立审查无其他问题或搁置项；修复以 RED→GREEN 和完整回归验证，不另开复审。


## 修复后的最终回归

恢复契约的实际预算判断修正后，memchr 和 PCRE 构建分别通过全部 **36 个故障／调度／预算组合**及普通搜索／runner／非法输入契约；所有目标故障均精确触发一次。最终默认 ci_build、**99/99 CTest**、Python **148 项（3 项跳过）**、原外部语料契约再次通过。测量前完成全部构建和测试，没有再修改影响二进制的代码。

## 固定 CPU 的正式对照

始终绑定 CPU **0／2／4**，sysfs 确认为三个独立 P 核。8 个固定 Android **模拟**场景（errno、boolean、boolean-inverse、multi16，各 1／2 个匹配节点），每份文件 65536 行，chunk 1024。每个预算两轮，按 1→2→3 再 3→2→1 的顺序交错；每组使用 ABBA／BAAB 及 Qt 同实现控制。两个两轮报告完整保留，合并只调整轮次编号并重新计算中位数。

总计 **768 条计时、192 条独立 profile**，全部通过原独立 oracle。每条记录的 CPU 默认并行度都为 **3**，实际全局预算分别严格为 **1／2／3**；元数据、源码、外部 PCRE、二进制摘要和汇总中位数另行核对。Linux、i7-14700、Qt 6.11.1、GCC 15.2、Release、LTO OFF、未锁频；正式计时无并行构建／测试，不混用前一轮不同二进制的绝对耗时。

| 同一查询 dmesg-boolean-t2 | Qt 轮询 ms | Qt 通知 ms | 轮询／通知 | 进程 CPU 轮询→通知 ms | 通知等待／轮询 sleep 中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全局上限 1 | 17.364 | 17.758 | 0.978 | 17.507→17.922 | 0／0 |
| 全局上限 2 | 15.612 | 16.001 | 0.976 | 17.051→17.682 | 58／13.5 |
| 全局上限 3 | 11.509 | 7.193 | 1.600 | 17.863→15.398 | 53／10 |

上限 1 时，生产者参与图执行，全部场景的两种调度均没有通知等待或轮询 sleep；两者接近，同实现控制倍率 **0.978～1.019**。这是“没有等待就没有通知消除轮询延迟收益”的对照，不把小幅差异解释为正则后端变化。

上限 2 时，常规最多一个后台 worker，两个匹配节点不能保证两个后台 worker 持续执行。目标布尔查询通知三轮稍慢、一轮稍快，汇总约慢 **2.5%**、CPU 增加约 **3.7%**；Qt 控制倍率 **0.980～1.026**，因此该小差异需要保守解读，不能单凭它锁定 mutex。

只把上限增加到 3（可用物理 CPU 完全不变），目标查询的通知耗时 **16.001→7.193 ms**，轮询 **15.612→11.509 ms**。该预算下通知四轮均比轮询快，汇总约 **1.60 倍**、CPU 降低约 **13.8%**。这比上一轮同时更换硬件／预算的对照更明确地证明了**执行预算会显著影响这条流水线**。它仍是整个任务的效果，未将其中收益精确分摊给某个锁、调度函数或具体线程。

上限 3 的 Qt 控制倍率范围 **0.950～1.002**；multi16 双节点仍观察到约 **10.2% wall** 和 **8.9% CPU** 退化，不能因为预算更充足就认为通知必然更优。上限 2 的同一负载约持平（149.073→147.420 ms），说明负载与调度预算共同影响结果。保留所有样本，不选择性排除重正则退化。

## 决定与下一步

**生产继续原 Qt／轮询。** 已确认预算是重要因素，仍未证明对所有负载的通知收益；没有调大应用的全局 TBB 上限，也没有添加按查询名称或正则内容的特判。

下一步可在显式实验中验证“名额不足时由提交线程协助执行已接纳任务”，并与原轮询／通知三方比较；这针对已经确认的预算限制，不扩大队列、不增加线程库。重正则退化仍须作为准入用例保留，不能只盯住布尔查询变快。perf 权限未调整，尚无精确锁热点证据，不追加 Windows 验证。
