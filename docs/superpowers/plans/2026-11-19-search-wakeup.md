## 审查重点

释放必须发生在 limiter 递减之后，检查和等待不能丢通知；取消／异常析构不得悬空访问同步对象；容量不变且 Qt 匹配路径明确；计时角色间重置无竞态；CPU 采样区间与 wall 相符；报告完整性及旧候选兼容。

## 已确认的验证边界

额外把整个进程绑定到单个 CPU 时，固定契约在原轮询模式即停滞。独立复现使用 `taskset -c 0`、`--candidate qt`、`dmesg-errno-t1`（65536 行、1024 行 chunk），将查询超时设为 2000 ms，得到退出码 1 和 `Worker search timeout`。原契约的同步操作没有外部事件循环超时，因此已主动终止该次停滞进程。

这证明原路径也有单 CPU 限制，不能只归因于通知方案；未完成其全部根因及修复，不把单 CPU 验证标成通过。本轮只在原正式评估同样的两个 CPU 亲和性下比较，结果不作为直接生产切换的依据。该限制应在后续调度准入中优先调查，不用扩大线程数或改测试预期掩盖。

## 完成结论（2026-11-19）

**通知方案值得继续推进，但本轮保留独立实验，不切换默认应用。** 不更换 Qt、不新增依赖，部分单线程 dmesg 查询完整耗时从约 23 ms 降至 9～10 ms，普通查询取消延迟也明显下降；进程 CPU 时间未出现与加速幅度相当的上升。重正则负载和部分双线程场景没有稳定收益，首次命中没有普遍改善。

现有单 CPU 停滞及图异常收尾仍需先处理，然后才能评估生产采用。它们是这轮调查发现／确认的准入问题，不声称通知方案已经修复。

### 实现及正确性

- 只在 `ZZLOGG_EXPERIMENTAL_SEARCH` 副本中编译 gate 和接入分支。`wake` 明确使用原 Qt matcher，不创建 PCRE／memchr 批匹配器；原生产对象中没有实验符号。原候选构建和运行入口保留。
- 容量检查、释放计数和 predicate wait 使用同一 mutex；释放先递减 limiter，再递增代数并通知，避免检查与入睡间丢通知。结果处理取消早退也由 scope guard 释放，wake 不连接原 decrementer 边，避免双重释放。
- 没有把限额改大：依旧线程数 × 3 个已接纳块，以及生产者手里一个已读取的待提交块。同步门在图之前声明，生命周期覆盖图；每次切换角色前，worker 已销毁并 join。
- 固定通知契约先在轮询占位实现失败，再通过通知实现。覆盖提前释放、拒绝后释放、不释放时取消、4096 次并发有界提交；真实 worker 的两种调度均覆盖完整结果、布尔／反选、编码、长行、取消／重搜、预取消、尾行更新及旧结果移除。
- 超时仍为 1 ms，目的为没有完成通知时检查取消；不是忙等或更短轮询。单次正则／转码仍不可中断，不给出严格实时取消上界。

### 测量方法

复用 Android **模拟日志**：dmesg、logcat、应用各 65536 行，异常边界 12 行，共 24938730 字节；内容 SHA 与上一轮一致。10 类主日志查询、5 类边界查询，各 1／2 匹配线程，chunk 为 1024 行，共 30 场景。

四轮交换进程顺序与 ABBA／BAAB，包含 Qt+通知 对照 Qt+轮询，以及 Qt／Qt 同实现控制。共 **960 条计时、240 条独立进程诊断**，全部 1200 条完整结果、文件和查询配置摘要与独立 oracle 一致。主日志每次全量搜索实际释放 64 次容量，边界 1 次；wake 的 poll_sleeps、候选 regex matcher 数均为零，取消后 live matcher／block 为零。所有主日志取消诊断实际中止在文件结束前。

Linux x86_64、Intel Core i7-14700、CPU 0／1、Qt 6.11.1、GCC 15.2、Release、LTO OFF、未锁频。正式计时没有并行构建／测试／调试器负载；只读审查不运行基准或构建。输入快照和索引在计时前完成，每次重新创建 worker；计时含提交、搜索、结果收集与销毁／join。

进程 CPU 通过 `getrusage(RUSAGE_SELF)` 的 user+system 累计时间差获得，起止紧邻 wall 时钟，覆盖同一任务区间（相邻读钟存在微小差别）。包括全部进程线程及背景活动，可能大于墙钟，不代表整机 CPU 百分比。不支持的环境返回 -1／汇总 null。本轮 Linux 记录均有有效 CPU 时间。

主日志通知／轮询 CPU 中位数比为 **0.918～1.033**，没有观察到靠显著增加 CPU 换取墙钟收益；这不等于所有场景都节省 CPU。首次命中多接近原值，个别更慢，符合通知主要消除后续满队列等待的作用范围；它是主线程收到非零累计命中通知，不代表 GUI 绘制。

除 16 模式场景外，主日志取消中位数从约 **0.770～0.971 ms** 降到约 **0.021～0.434 ms**；重正则场景仍约 3 ms，不能承诺普遍或严格上界。边界一块的取消主要是收尾，不算有效中途取消。未命中场景首命中为 -1。

主日志普通单线程场景原轮询通常 sleep 21 次，新方案通常等待 60～61 次，但超时中位数为 0：等待次数更多而每次能够被及时唤醒。双线程多数等待 55～58 次、超时中位数为 0。16 模式场景单／双线程通知等待中位数为 197.5／180，超时为 136.5／122，仍需 1 ms 超时检查取消，吞吐没有改善。等待次数／超时次数是路由诊断，不是 CPU 用量，未把二者混用。

- 新增同步门固定契约及扩展后的 wake 报告测试通过；错误释放次数、丢路由、误入轮询或新 matcher 都会被拒收。小规模 30 场景冒烟的 240 条计时／60 条诊断也通过，但其并行构建期间耗时不作性能证据。

- `nm -C` 确认默认 `libklogg_logdata.a` 没有 WakeupGate 或 experimental 符号。未新增生产第三方依赖或改变默认调度。
