# P11 补充：StringZilla 查找内核对照

**基线：** `576554c`。继续已确认的 P11 路线，复用同一套逐行逐模式契约与 147 场景矩阵，不改变生产搜索实现。

## 设计与取舍

选择 StringZilla v5.3.2，提交 `1c78fe5d288e3abb3bd1583f291c4f3d292133d4`，Apache-2.0。仅在独立实验中引用其查找头文件；正式 vendor、应用构建和默认 CI 均不增加依赖。源码存放在 `out/benchmarks/p11-stringzilla/`，配置只读本地来源，既不自动下载，也不追踪浮动版本。

比较两个入口：`stringzilla-serial` 使用公开串行内核；`stringzilla` 在本轮支持的 GCC／Clang x86_64 环境中检查 AVX2、BMI、BMI2、LZCNT 等需求后选择 Haswell 内核，否则串行。只编译查找所需头文件，避免为实验引入上游完整动态库的无关功能。此选择器仅为实验，不能当作跨平台生产分派方案；Windows／ARM 等平台策略另行验证。

保持原有完整位图和 UTF-8／查询回退规则；每个模式调用一次查找，不把存在某个命中代替全部子模式结果。StringZilla 的无状态调用与 memchr 的可复用 Finder 存在 API 成本差异，构造、首次及热扫描共同报告。

## 准入边界

本轮仍是内核／批量接口实验，不含实际用户日志、完整索引／UI、取消、峰值内存、Windows／macOS／ARM 或 Hyperscan／Vectorscan 对照。即使胜出也不能直接承诺整应用性能或所有输入无退化；若结果不支持采用，保留生产实现。

## 结果与决定

**本轮不把 StringZilla 接入生产。** Haswell 内核在这批有效输入上明显快于配对 Qt，但与 memchr 的直接对照没有显示出更快的场景，多数明显更慢；接近 1 的差异不作排名。它不需要 Rust 工具链、构造较轻，仍可保留为实验备选。下一步优先用独立探针测量 memchr 在实际 PatternMatcher／搜索管线中的收益、逐行与批量接口成本，证据充分后再决定是否值得新增依赖。

### 环境与统计

Linux x86_64、Intel Core i7-14700，固定 CPU 0、未锁频；Qt 6.11.1、GCC 15.2.0、Release `-O3 -DNDEBUG`、C++ LTO 关闭；rustc 1.100.0、memchr 2.8.3。StringZilla 记录的实际内核为 `StringZilla 5.3.2 haswell` 和 `StringZilla 5.3.2 serial`。

同一二进制运行两组：相对 Qt 的 StringZilla／串行版本／memchr／Qt 控制，以及相对 memchr 的 StringZilla／memchr 控制。每组每候选 147 场景、4 轮，合计 14,112 条热扫描记录；每侧每场景 8 个热样本，构造和首次扫描各 4 次独立测量。倍率为参考耗时中位数除以候选耗时中位数，大于 1 表示候选更快。每批 128 行；保留原有编码验证、Qt 回退、结果分配、完整位图及 checksum 成本。

99 个合格输入场景包括 96 个常规 ASCII／有效 UTF-8 场景与 3 个压力场景；另有 48 个异常 UTF-8 回退场景，不混入有效输入性能结论。以下最小／中位／最大值是各场景倍率的分布，不能解释为整应用倍数。

| 候选与参考 | 合格输入倍率最小／中位／最大 |
| --- | ---: |
| StringZilla Haswell / Qt | 1.607 / 5.902 / 97.496 |
| StringZilla serial / Qt | 1.074 / 3.752 / 42.994 |
| memchr / Qt | 1.632 / 14.507 / 150.879 |
| Qt / Qt 控制 | 0.635 / 1.001 / 1.517 |
| StringZilla Haswell / memchr | 0.209 / 0.782 / 0.994 |
| memchr / memchr 控制 | 0.992 / 1.001 / 1.015 |

Qt 控制在全部场景中的范围为 0.466～1.517，存在明显布局／JIT／系统噪声影响；串行内核相对 Qt 的小幅差异不足以证明收益。直接 memchr 控制在合格输入中稳定得多，但异常输入回退到 Qt 后范围扩大至 0.780～1.318。不能从回退场景的小幅时差推断某个字节库更快。

### 直接配对的代表场景

下表来自 `--reference memchr`；热扫描单位为 ns／行，包含每行所有模式的完整结果。

| 场景 | memchr | StringZilla Haswell | memchr 耗时 / StringZilla 耗时 |
| --- | ---: | ---: | ---: |
| ASCII 128 字节、1 个短关键词、h50 | 13.98 | 17.26 | 0.810 |
| ASCII 4096 字节、64 个长关键词、h0 | 5427.15 | 7290.57 | 0.744 |
| Unicode 4096 字节、16 个短关键词、h50 | 3081.17 | 3407.28 | 0.904 |
| 长公共前缀 4096 字节、1 个关键词、未命中 | 172.61 | 200.40 | 0.861 |
| 长公共前缀 4096 字节、64 个关键词、未命中 | 5303.19 | 7129.59 | 0.744 |
| 高重叠 4096 字节、64 模式中 1 个未命中 | 1008.36 | 1603.51 | 0.629 |
| ASCII 128 字节、64 个长关键词、h100 | 394.97 | 1890.20 | 0.209 |

最后一行是本轮最大差距，StringZilla 约慢 4.79 倍。h100 代表每行注入某个模式，不代表所有模式都命中。该结果针对选定版本、公开无状态 Haswell API 与当前适配方式，不能推广为所有 StringZilla API、版本或硬件都慢于 memchr。

### 构造、首次与维护成本

以直接配对的 ASCII 4096 字节／64 个长关键词／h0 为例，StringZilla 构造为 11.92 μs、首批扫描 0.954 ms；memchr 为 19.51 μs、0.712 ms。StringZilla 构造较轻，memchr 的复用 Finder 在本轮热扫描更有优势。首批含 128 行，不等于首次一行延迟，也不是全新进程冷启动；未测峰值内存或完整分配成本。

源码存档为 2,362,747 字节，固定的 170 个头文件加许可证合计 5,983,927 字节。头文件／许可证 manifest 指纹为 `c8e647acc14b7ca8c9a3d1c52d8057ce2b94905cd21df8234b8cfd6a7253b9d6`。本适配层的实际编译依赖闭包为 27 个上游头文件、376,680 字节；这不表示可以忽略许可证或直接删除其余上游文件。

同配置、均不启用 Rust 的最终独立 C++ 工具对照：

| 构建 | 文件字节 | GNU size text 字节 |
| --- | ---: | ---: |
| 不含 StringZilla | 297,880 | 240,527 |
| 包含 StringZilla 两种入口 | 319,408 | 256,729 |
| 增量 | 21,528 | 16,202 |

这是实验工具的默认链接产物差值，含适配代码和符号，不是应用安装包的预计增量。StringZilla 无须新增语言工具链，但仍增加源码、许可证、版本锁定及平台分派维护；仅有相对 Qt 的局部收益不足以跳过实际应用准入。

### 验证与复现

- 三种 Release 独立构建通过：无新增候选（3 后端）、仅 StringZilla（5 后端）、StringZilla 与 Rust（7 后端）。完整位图、1,024 条确定性随机输入、SIMD 边界和 Linux 保护页契约全部通过。
- 审查后补足长度 9、页尾前 0～32 字节命中以及四处内部字节不匹配；独立只读审查未发现阻塞项。
- 147 场景跨轮输入／结果摘要一致；非 Qt 参考额外在计时外对照真实 Qt。默认 Qt、std 参考及 memchr 参考的 runner 冒烟通过；不含 Rust 的构建会拒绝 memchr 参考。
- 串行适配层不定义 SIMD 开关也能编译；伪造来源因固定指纹不匹配被 CMake 拒绝。
- 项目 `ci_build` 成功，离屏 CTest 97/97 通过；Python CI 124 项、3 项跳过、无失败。上述是本机 Linux 验证，未执行 Windows／macOS／ARM 原生验证。
