# 搜索 worker 单 CPU 与异常收尾修复

> 使用 systematic-debugging、test-driven-development 和 executing-plans，最后一次独立审查。沿用本地 master 中文提交授权，不推送。

**目标：** 修复真实生产 worker 在只有一个 TBB 执行名额时停滞，以及生产者／任务异常时节点生命周期和完成通知问题；通知调度和正则候选仍保留实验。
**设计：** 使用显式 isolated task_group_context 观察后台取消；无可用 TBB 后台执行名额时，由生产者在容量不足处 wait_for_all 参与执行已提交任务。正常多 CPU 继续原调度。生产者和最终等待的 catch 在所有节点仍存活时 cancel+drain，保留原异常。失败清除并撤回已有匹配，发出唯一终态进度和完成通知，再沿用原错误报告。
**技术栈：** 已有 C++17、Qt、oneTBB、Python 标准库，不新增依赖。

- [x] 固定生产测试限制 TBB 并行度为 1，真实文件大于队列容量，外部超时确认旧版停滞。

- [x] 修复生产单 CPU 进度和上下文取消观察；异常先停止并等待图，再销毁节点；补失败终态及撤回。
- [x] 运行单 CPU 亲和性与 global_control 限制、两种实验调度、失败矩阵、默认构建／CTest／Python CI 与加速后端回归。
- [x] 一次独立审查，必要修复；用原 Android 四轮对照检查多 CPU 改动影响，更新路线图并中文提交。

## 测试与边界

生产默认的单 CPU 测试直接链接原 klogg_logdata，不依赖 Rust／PCRE；实验故障钩子仅在已有 ZZLOGG_EXPERIMENTAL_SEARCH 副本中编译，测试真实图和操作，不模拟完整 worker。故障仅触发一次 bad_alloc 或读错误，不宣称进程持续耗尽内存时仍可分配 Qt 错误消息。硬超时、故障点、匹配回退及 complete 信号均为实际运行断言。

## 审查重点

arena/global_control 的单执行名额识别，参与图任务时的取消响应；group context 状态必须线程安全；异常排空时节点和 lambda 捕获仍存活，二次异常不得覆盖原异常；失败撤回已交付结果且不伪造完整进度缓存；测试钩子不进入生产，单 CPU 检查必须有硬超时。

## 实现与根因（2026-11-19）

**两条生产问题已修复；默认仍采用 Qt 和原多 CPU 轮询。** 通知调度、PCRE2 候选保持实验，不增加第三方依赖。

单执行名额时，生产者占着 TBB 需要参与执行的名额，却在满队列前 sleep；没有后台执行名额推进图，容量无法释放。生产测试直接将 `global_control::max_allowed_parallelism` 设为 1，旧版在 4 秒内无进展；修复后，容量不足时 `wait_for_all()` 让生产者执行已接纳的有界任务。也检查 `this_task_arena::max_concurrency()`，覆盖 arena 自身限为 1 的情况。既有容量上限不增加，取消仍通过原标志检查，单次匹配／转码不会被强行中断。

异常路径原来依赖 graph 析构时等待，但节点和 lambda 捕获在栈上声明于 graph 之后，先析构后才等待会产生悬空访问。现在显式 isolated context 供提交线程检查任务取消，连边、读取、块构造、提交和最终等待全部在保护范围内；异常时先 cancel，再在全部节点仍存活时 wait，二次异常不会覆盖原异常。仅查看 `graph.is_cancelled()` 不够，因为该状态由等待过程更新；提交阶段使用 context 的线程安全取消查询。

失败后使用 `SearchData::invalidate()` 保留撤回集合：已被界面消费过的匹配和未消费的匹配都从完整集合中撤回，已有尾行撤回也不丢失。清零匹配数、宽度和已处理范围，发送唯一终态进度与完成信号，再沿用原错误报告。正数文件范围不会因为失败被误标为完整可缓存结果；同一个 worker 可以重新完整搜索。

### 测试证据

- 生产默认新增独立 CTest `zzlogg_ui.search_worker_recovery`，直接链接 `klogg_logdata`，不要求 Rust 或 PCRE。它测试 global_control(1) 下 1／2 个匹配节点的全量和取消，以及单槽 arena 完整匹配；固定结果是偶数行、4096 次匹配、tab 展开宽度 11。CTest 硬超时 30 秒，异步搜索内部另有 4 秒限时。
- 初次测试配置遗漏初始化时先修正测试设置，再观察旧生产代码在 `Single-slot search made no progress before deadline` 处真实失败；修复后通过。整个生产测试和既有 probe 完整契约也都在 Linux CPU 0 亲和性下通过。
- 原 Android 复现使用相同 65536 行 dmesg、1024 行 chunk、Qt 和 CPU 0，查询 deadline 2000 ms；旧版超时，最终代码四次完整结果均在限时内通过，结果摘要／命中数／配置身份与独立预期一致。
- 独立故障矩阵覆盖 **连边、读块、块分配、匹配器、结果合并、首次读块** 六处，每处分别执行 poll／wake；每个子进程检查完整搜索失败、追加更新失败及同 worker 完整重搜。全部 12 个组合在 CPU 0 与 CPU 0／1 各通过，子进程硬超时 20 秒。
- 多 CPU 读块／分配错误让一个真实 matcher callback 保持活跃，直到异常清理开始才释放；旧版在销毁节点前以退出码 70 捕获活跃回调，避免测试故意制造实际 UAF。单 CPU 对应检查尚未执行的排队任务被安全取消。合并故障先等待部分结果被消费，再触发失败，验证撤回真实已交付结果。
- 旧版首次读取／matcher 错误没有终态，固定契约先失败；最终代码要求恰好一个终态和完成，错误报告一次、异常排空一次，失败后可见匹配为空，处理范围为零。最终销毁后活跃 callback、block、候选 matcher 均为零。
- 故障钩子及阻塞安排仅编译进已有实验副本。真实生产代码的图、上下文、错误处理和结果集合被执行，测试只抑制故障模式下的错误弹窗。一次性 bad_alloc 不是持续全进程内存耗尽的承诺。

### 审查与修复

一次新鲜只读独立审查发现一个 Important：TBB `buffer_node::register_successor()` 即使尚无输入，也会安排内部转发任务；原方案的 try 只包住提交而未包住连边。核对仓库内 oneTBB 后确认成立。新增连边后故障测试，旧保护范围在 CPU 0 下以退出码 71 失败；将全部 make_edge 纳入 cancel/drain 范围后通过，随后重跑整套回归。这是唯一修复轮，没有以作者推测代替回归证据。

一项 Minor 延后：默认生产单槽测试每次建立新 worker，arena 分支也只验证完整匹配；后续可补同 worker 复用、arena 的取消／终态／重搜，并减少很短异步取消的时序依赖。**当前同 worker 失败重搜由显式故障矩阵覆盖，不将默认 CTest 的覆盖说成同 worker 重用。** 文档已按实际范围表述。
