# ZzLogg 基于 ZzPureTools 的 UI 重构路线

## 1. 目标与约束

以 `master` 为基础重新组织 UI，使应用窗口从创建时就使用 ZzPureTools 标题栏和主题。保留现有屏幕布局与日志功能，最终将应用侧 UI 实现集中到 `src/ui/`。

本次规划依据：主仓库 `248fc7c5`，工作区 ZzPureTools 已更新至 `d6b90f1`。编码检测改造属于独立任务，不纳入本路线。`main` 分支的 FluentUI3Style 不参与合并。

- 保持图标、菜单、居中标题、窗口按钮的标题栏组织；保持已有主题和置顶入口。
- 保持工具栏、文件标签、原始日志、过滤结果、快速查找及状态信息的位置和操作习惯。
- 用户主题选择仅深色、浅色，支持已有语言动态切换。
- 保留配置键、存储目录选择、会话、收藏、快捷键和应用品牌。
- 保留日志读取、索引、搜索和高性能自绘视图。
- 使用框架实际存在的公开 API；Qt 的 `QMainWindow` 仍是宿主窗口。
- 每阶段交付可独立运行的程序，维持一个默认 GUI 可执行文件。

## 2. 为什么要调整现有实现

现有 `MainWindow` 先生成菜单，`KloggApp::newWindow()` 再通过装饰回调安装 `ZzLoggFluentShell`，将菜单动作迁入标题栏。这增加了菜单所有权、弹出窗口属性和失败回滚的处理。

`src/ui2` 当前包含运行时主题和窗口外观接入；`src/ui` 仍负责业务控件。重构重点是把窗口创建、主题依赖和组件责任整理清楚，不是简单改目录名。

ZzPureTools 已提供 `ZzFluentTitleBar::menuBar()`，返回框架拥有的 `QMenuBar`。应用可以直接向它创建菜单，无须先建立一个旧菜单栏。

## 3. 保留、改造与删除清单

| 类别 | 内容 | 处理 |
| --- | --- | --- |
| 日志核心 | `src/logdata`、`src/regex`、`src/filewatch` | 复用，第一阶段不改变行为 |
| 文本绘制 | `AbstractLogView`、`LogMainView`、`FilteredView` | 保留；后续按需要收敛主题和输入接口 |
| 单文件页 | `CrawlerWidget` | 第一阶段整体接入；后续拆出搜索和页面组合 |
| 主窗口 | `MainWindow` | 保留对外接口与会话连接，重写外观初始化，分离菜单/工具栏构建 |
| 框架接入 | `ZzLoggFluentShell`、`ZzLoggUiRuntime` | 提取职责到 `src/ui`，移除创建后装饰和菜单迁移 |
| 通用框架 | ZzPureTools | 使用公开接口，应用适配放在主仓库 |
| 配置和存储 | `Configuration`、`src/storage` | 保留数据格式、迁移与启动语义 |
| 测试 | `tests/ui2` | 保留有效行为测试；改写菜单迁移等过渡架构测试 |
| 过渡目录 | `src/ui2` | 第一阶段依赖迁移和测试通过后删除 |

当前 `cmake/ZzPureTools.cmake` 明确启用动态库。此次 UI 结构调整沿用现有链接方式，避免把静态打包改造混入界面迁移。

## 4. 组件边界

| 组件 | 拥有内容 | 对外责任 |
| --- | --- | --- |
| 应用运行时 | 一个主题控制器、全局样式 | 向所有窗口提供同一主题服务 |
| MainWindow | 会话关联、窗口级动作、页面与外观组件 | 文件操作、窗口管理、协调当前文档 |
| WindowChrome | 标题栏接入和窗口代理 | 暴露菜单容器；同步标题、图标和窗口状态 |
| 文件工作区 | 文件标签和活动文件关联 | 切换、关闭、空工作区状态 |
| 日志页面 | 主视图、结果页和分割布局 | 组合已有数据与自绘视图 |
| 搜索面板 | 输入、搜索选项、状态显示 | 发出用户意图，展示搜索进度 |
| 设置窗口 | 各设置页 | 编辑配置，通过现有存储服务保存 |

标题栏发出的窗口意图由宿主执行。它不会自行替代应用的退出确认、会话保存或重启流程。

## 5. 分阶段交付

### 阶段一：直接创建 ZzPureTools 主窗口

完成主题依赖传递、标题栏和菜单原位创建、工具栏组合、窗口状态同步，接入现有文件标签和 `CrawlerWidget`。迁移并删除 `src/ui2`，保持现有公开窗口接口和测试入口。

交付：可以运行对比的新主窗口，以及完整依赖的 Windows 运行目录。详细步骤见 [阶段一实现计划](2026-09-07-zzpuretools-window-phase1.md)。

### 阶段二：拆分文件工作区

从 `MainWindow` 中抽取标签增删、活动文件切换和空工作区状态。保持 `WindowSession`、`SignalMux`、`QuickFindMux` 的语义，确保最后一个标签可关闭，多窗口和会话恢复正常。

验收：打开多个文件、拖动排序、关闭活动/非活动/最后一个文件、重开文件、退出并恢复会话；动作状态与当前文件一致。

### 阶段三：拆分日志页面与搜索面板

从 `CrawlerWidget::setup()` 和搜索选项处理里抽取独立搜索组件。初期采用现有控件组合；只有确认框架控件满足原交互语义时才替换。保持过滤任务在数据层，主视图和过滤视图继续复用。

验收：普通/正则/布尔搜索、取消搜索、持续追加刷新、保留多组结果、结果定位原文、快速查找和快捷键均可用。

### 阶段四：设置与辅助窗口

按主题、字体、搜索、文件监控、存储等职责组织设置页面；高亮、预定义过滤和草稿窗口逐一适配统一主题。保留配置字段和存储迁移流程。

验收：设置保存后重新打开一致；中英文切换即时生效；深浅色下文字、背景、选择状态可读；取消操作不意外保存。

### 阶段五：清理与跨平台验收

删除确认失去调用者的适配代码，更新学习指南、构建说明和测试名称兼容策略。分别在 Windows、Linux、macOS 上验证窗口、菜单和输入，不将 Windows 结果视为其他平台通过。

验收：单一默认 GUI、完整运行依赖、旧配置和会话可读取；代表性大文件打开、滚动、搜索及内存占用与基线对比无明显退化。

阶段二至五是交付边界，不是本次可以盲目执行的全部代码变更。每阶段开始前根据已完成代码编写对应文件和接口级实施任务，避免一次引入全部新抽象。

## 6. 主要风险与约束处理

- **菜单容器**：安装标题栏后不调用 `QMainWindow::menuBar()` 来创建业务菜单，全部通过指定容器；迁移所有现有调用点。
- **生命周期**：窗口先于主题服务销毁；窗口代理先于其使用的标题栏销毁；延迟回调绑定 QObject 上下文。
- **主题一致性**：同一应用仅一个活动主题控制器，标题栏、设置、多窗口都调用它；保留日志绘制缓存刷新。
- **平台能力**：依据 `ZzWindowAgent::capabilities()` 决定原生系统按钮策略，不写死 Windows 假设。
- **失败行为**：代理附着失败时保留可关闭的原生窗口和可用菜单，清晰记录错误；不留下半配置无边框窗口。
- **性能**：UI 线程不承担大文件扫描或搜索；自绘视图不换成承载全文的普通文本框。
