# P5：同一行只解码一次

**基线：** `302a354`；按已确认的依赖优化路线执行。

**目标：** 默认 Qt 正则后端在匹配非空模式列表时只解码一份 UTF-8 输入，保持逐模式结果、顺序、大小写、Unicode 和布尔搜索语义。

**设计：** 在 `DefaultRegularExpressionMatcher::match()` 内，零模式直接返回空结果；其余情况在循环前用原来的显式长度 `QString::fromUtf8()` 转换，lambda 按引用读取局部 const QString。生命周期覆盖整个同步循环，不保存跨行状态。与保持现状相比，减少重复解码及分配；与跨行缓存或换引擎相比，不增加缓存失效、线程同步或语义兼容成本。

## 范围与文件

- `src/regex/include/hsregularexpression.h`：仅修改默认匹配器的解码位置。
- `tests/unit/patternmatcher_test.cpp`：补齐直接匹配器边界用例与逐模式参考结果对照。
- `tools/benchmarks/regex_decode/`：独立构建的可复现探针，使用实际项目头文件与 Qt，测热匹配吞吐；Linux/glibc 下独立测量分配次数与请求字节，不把累计申请量称为峰值内存。
- `scripts/dev/benchmark_regex_decode.py`：从 Git 提取旧头文件，与当前工作树交替测量，输出原始 JSON 和摘要。大样本及构建产物保存在忽略目录 `out/benchmarks/p5-regex-decode/`。
- 总路线和本记录：登记结果、采用决定与原生平台边界。

## 验收与限制

语义对照必须通过；无法解释的差异或稳定退化先调查，不以“减少解码次数”直接宣称应用变快。测量固定为 Linux、Qt 6.11.1、GCC、Release、LTO OFF，先预热再交替执行；时间测量与分配插桩分开。探针测的是已构建匹配器的内存内热扫描，不包含磁盘 I/O、查询首次编译、索引、UI 或整应用端到端速度。P5 不更换正则引擎，不修改布尔解析器，不引入新运行依赖；Windows/macOS 原生验证由 CI 补齐。

## 结果

**决定：采用。** 保留原 Qt 引擎、匹配 API、显式长度与结果顺序，仅移动局部解码的位置。行为测试和对照摘要通过，非空多模式分配确定减少；中文及非法 UTF-8 多模式探针收益超过相同源码控制偏差。没有证据支持承诺所有场景更快。

- 原实现上新增 `[patternmatcher]` 测试通过：298 个断言、4 个用例。优化前 `--require-savings` 按预期失败，优化后通过（非空多模式分配减少、零／单模式分配不变）。

- Linux x86_64、Intel Core i7-14700、GCC 15.2.0、Qt 6.11.1、CMake 4.3.3。应用为 Release、LTO OFF、WARNINGS_AS_ERRORS ON、两组测试 ON、Hyperscan/VectorScan OFF；探针为 Release `-O3 -DNDEBUG`、LTO OFF、默认 Qt JIT，固定 CPU 0、未锁频。Windows/macOS 原生验证尚未执行。

### 性能与分配

两个真实头文件在同一进程内经相同调用边界比较，两版均先校验和预热，再复用实例按 ABBA 计时，8 轮各版 16 次采样。原始输入和结果 SHA-256 在所有轮次相同。实现和命令见 [探针说明](../../../tools/benchmarks/regex_decode/README.md)；原始数据位于本机忽略目录 `out/benchmarks/p5-regex-decode/`。

```bash
python3 scripts/dev/benchmark_regex_decode.py \
  --qt-root /home/zz/Qt/6.11.1/gcc_64 \
  --mimalloc-library out/build/p4-throttler/output/libmimalloc.a \
```

### 性能调查与结论边界

初次独立进程测量和初版进程内顺序测量中，部分单模式样本偏慢。审查发现先测者偏快的顺序效应，因此改为两版都预热后 ABBA 测量，并加入 `--current-ref 302a354` 的相同源码控制。控制使用两份 SHA-256 完全一致的旧头文件；数据在 `out/benchmarks/p5-regex-decode-abba-control/`。

即使相同源码，长 ASCII 单模式仍出现 7,901→11,355 ns/行，短 ASCII 4 模式出现 918→1,142 ns/行的偏差；真实改动的短 ASCII 单模式在不同实验中也改变了快慢方向。因此，本环境的 ASCII 计时不足以归因于代码变化，也不能靠负对照证明不存在退化。中文及非法 UTF-8 多模式的控制比值接近 1，真实改动的改善幅度明显大于控制偏差。

**验收限制：单模式及 ASCII 的吞吐无法得到可靠结论；没有把原计划的“单模式无稳定退化”当成已证明的保证。** 可确认的是零／单模式仍不增加解码或分配，结果兼容，多模式减少解码和分配，且上述 Unicode 样本有可重复收益。采用这一局部改动，后续仍可在稳定原生环境复测；不要把探针收益扩大为端到端搜索、首次查询、取消响应、UI 或启动性能。
