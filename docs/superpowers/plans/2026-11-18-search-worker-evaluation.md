# P11：完整后台任务实验计划

> 使用 executing-plans 执行已确认路线；沿用本地 master 中文提交、不推送。

**目标：** 在实际文件索引、LogFilteredDataWorker 和 TBB 调度中验证 memchr 候选的完整行结果、进度、取消、更新和回退。

**规格：** [组件评估后的下一步](2026-11-18-search-pipeline-evaluation.md)。生产保留 Qt，拒绝仅凭内核速度全量替换。

## 设计与实现方案

直接改变应用搜索会过早采用 Rust；复制 worker 算法则不能验证真实任务。采用独立实验目标，重编译真实 regex/logdata 源文件，仅该副本定义实验宏并链接既有锁定 Rust crate。应用和默认 all／ci_build 不链接副本，不查找 Rust。已有组件探针共用实验 Rust 构建描述。

PatternMatcher 的实验副本从生产解析后的 subPatterns 创建候选，复用原有 BooleanExpressionEvaluator 和反选；无需复制或限制查询语法。不合格查询直接走原有逐行路径；异常 UTF-8／BOM 保留前轮逐行 Qt 回退。默认工具后端 Qt，显式选择 memchr 才启用。

代理选择每批最多 128 行、256 KiB UTF-8 输入；该值是本轮实验参数，不是用户决定或最终最优值。超过 256 KiB 的单行直接调用原有 Qt。取消在转换前后、批次间检查，未完成块的结果不发布；不改现有取消后也发终止 100 信号的约定。字节限额仅约束匹配子批次，不约束原始文件读取／整个块转码，超长行 Qt 调用依旧不可中断。

调查发现已有裸 SearchBlockData 在取消的消费出口和未入队出口泄漏。使用 TBB 可复制的 shared_ptr 传递所有权；该修复进入正常生产源码，其他候选行为仅存在于实验副本。通过副本内的生命周期计数先验证泄漏，再验证所有退出路径释放；计数实现只属于工具，正常编译没有诊断代码。

- `tools/benchmarks/search_worker/`：可选副本构建、批次适配／边界、诊断、完整任务契约和计时入口。
- `tools/benchmarks/literal_search/cmake/ProbeRust.cmake`：两个主工程探针共用离线锁定 Rust 目标。

- worker 默认代码修复块所有权；真实尾行更新验收同时发现并修复 RawLines 虚拟 EOF 读取／多字节解码错误；同一套现有应用测试必须通过。
- 数据是生成文件；实际索引和文件读取进入验收，但计时使用已索引文件／热页缓存，不能代表真实冷磁盘或用户日志。

## 审查重点

- 取消时队列内／尚未入队／正在匹配的块全部释放，不能发布不完整块或影响下一次搜索。
- 私有解析结果顺序、任意合法布尔组合／反选与候选位图必须一致；不合格查询不能进入 Rust。
- 字节边界、空行、超长单行不能死循环、溢出或突破子批次限额。
- 副本 ABI 宏与依赖传播不能污染正常应用，尤其不可意外链接原版和副本 regex/logdata。
- 终止进度信号与实际已处理行数要分开；不要把合成取消或页缓存数据写成平台延迟保证。

## 验证中发现的默认路径问题

实际尾行更新契约发现：索引用“文件大小 + 1”代表无 LF 的末行，而旧读取层把未读到的零填充字节留在缓冲区，导致 `^ERROR$` 漏掉末行 `ERROR`。UTF-16 的逐行解码还会减去两个字节，丢失最后一个字符。

本轮裁决是修复这个已有错误，而不让候选复刻错误行为。读取层识别索引的虚拟 LF，只读取真实的已索引字节，并将局部行尾偏移换成显示编码的 LF 宽度；不改变全局索引格式。真实短读返回空结果，不暴露零填充内容。即使文件在下次索引之前增长，也不把新增的首字节当作虚拟 LF。若此处理错误，风险是尾行显示／搜索回归，因此默认测试覆盖 UTF-8、UTF-16LE／BE、UTF-32LE × 有／无实际 NUL × 有／无换行，以及未重索引前追加和截断。

取消问题用实验生命周期计数先复现 `Cancelled search leaked live blocks`，RAII 修复后归零。尾行回归修复前出现 4 条断言失败；UTF-8 视图及 UTF-16 解码两层修复后，全部编码和尾部边界通过。候选路由也曾以未实现适配验证 `Eligible query did not use memchr batches`，再实现并通过。

## 2026-11-18 结果与决定

**完整后台任务中的 memchr 候选仍值得继续验证，但不进入默认应用。** 单关键词短行收益明显小于组件／内核实验，多关键词计算密集场景收益更大；查询直接回退接近 Qt，超长行回退本轮略慢。不能声称所有查询等速或更快，也不以跨场景中位数代表整个应用。

环境为 Linux x86_64、Intel Core i7-14700、固定 CPU 0/1，未锁频，Qt 6.11.1、GCC 15.2.0、rustc 1.100.0、memchr 2.8.3；主工程 Release，LTO OFF，严格警告开启，继承主工程 native 指令集设置。文件已索引且页缓存预热，1／2 指配置的匹配节点数量，不是整个进程只有这么多线程。worker 对象创建在计时前，提交搜索到任务释放在计时内。

22 场景 × 2 候选（含 Qt 控制）× 4 轮 × 4 个配对记录，共 **704 条计时记录**；每侧每场景八个样本。另有 **176 条诊断记录**。每次完整行结果、最大宽度和处理位置摘要都一致，跨轮输入签名一致。每次搜索重建匹配器；不复用匹配器来隐藏构造成本。

下表为 Qt／候选的耗时中位数之比，大于 1 表示候选快。14 个候选适用场景中含坏编码混合行和预过滤；嵌套 Boolean 合成场景为零命中，不能由它推断有命中时的合并成本，固定命中语义由契约测试覆盖。

Qt 控制最明显波动发生在双匹配线程的零命中 Boolean 场景，约 0.820 倍。小任务仍受调度和锁频状态影响，不以几个百分点作性能排名。超长行虽然回退 Qt，候选仍需建立额外匹配器和逐行检查限额，因此本轮有约 4%～5% 耗时增加。
