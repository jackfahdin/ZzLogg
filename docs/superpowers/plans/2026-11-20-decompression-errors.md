# P13 流式解压错误处理计划

> 使用 writing-plans／executing-plans 内联执行，最后一次新鲜上下文独立审查。

**目标：** 让损坏压缩日志及时失败，让写入失败不能误报成功，为后续 codec 评估建立基线。
**规格：** [错误处理设计](../specs/2026-11-20-decompression-errors-design.md)，执行既定路线 P13 的首轮正确性验证。
**架构／技术栈：** Qt C++ Decompressor、现有 KArchive、Qt Test，独立离线生成的 gzip／bzip2／xz 夹具。

## 全局约束

不更换三方库、不增加运行依赖、不改变支持格式和异步接口、不设置任意解压总量上限；便携更新策略保持不变。沿用本地 master 中文提交，不推送。

## 审查重点

- 损坏／截断流的零进展不能循环等待，也不能被当成正常空流；有界完成时间和准确返回值验证。
- 缓冲文件的写入成功不代表落盘成功；短写、写异常和 flush 失败均需返回 false。
- 预先取消／处理中取消均一次完成且关闭输出；成功、输入打开失败、异常路径也不遗留文件打开状态。
- 4 MiB 边界、二进制 NUL、中文和 CRLF 输出逐字节一致；不把同库压缩再解压当独立 oracle。
- 不改 vendor 和便携更新策略；原便携更新包回归及默认构建／全套测试继续通过。

## 本轮复现与修复

九种正常格式／数据组合在旧实现上均通过。三种格式各自的损坏与截断输入共六例，都在测试的 2 秒窗口内无法结束，必须由测试设置取消标志才能退出；短写和写入异常返回 true；输入打开失败留下已打开的输出文件。另用真实 `/dev/full` 验证了缓冲写入后关闭时失败却仍返回 true 的问题。普通 writeData 返回 -1 的场景原本就正确失败，不将其记成新增修复。

根因是调用方使用返回 QByteArray 的 read 接口，忽略读取失败及非正常结尾的空数据；写入只检查负数，没有拒绝短写；catch 只记录日志，结果仍保留 true；close 的缓冲刷新错误未进入返回值。

改为计数字节读取，零进展且非正常结尾立即失败；使用同一块 4 MiB 缓冲区；写入必须完整，结束前检查 flush；异常返回 false；通过作用域清理统一关闭输入输出。取消、读取错误和输出错误都沿用现有 finished(false)，UI 不加载失败的解压结果。部分临时文件继续由原调用方管理，不额外设置大小限制，也没有改 vendor 源码。

## 验证与范围

新增 `zzlogg_ui.decompressor` 独立测试进程，CTest 硬超时 45 秒；测试内部遇到不退出的读取循环会设置取消并等待 worker，确保引用对象仍存活。最终 Qt Test **24 项通过**（含初始化／清理），耗时约 0.05 秒。跨格式内容逐字节一致，完成信号与同步返回值一致且只发一次，所有已启动操作关闭输出。

九个压缩夹具由 Python 标准库离线生成，总压缩数据约 16.5 KiB；提交源码、夹具和内容摘要，运行 C++ 测试无需 Python、网络或系统压缩命令。`/dev/full` 用于原生缓冲刷新失败验证，不存在该设备的平台仅跳过此项；其他错误路径仍由真实 QFile 边界用例覆盖。

默认 `ci_build`、离屏 **100/100 CTest**（包含原便携更新包测试）通过；Python **149 项、3 项跳过**，无失败。独立夹具的压缩摘要、解压大小和内容摘要均另行核对。本轮没有进行压缩吞吐量对比，不把缓冲区复用宣称为已测得的性能收益。
