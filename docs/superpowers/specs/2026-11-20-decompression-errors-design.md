# P13 流式解压错误处理基线

延续依赖优化路线 P13，先验证现有 gzip／bzip2／xz 日志解压，修正阻碍后端对照的调用层错误。保持 KArchive fork、压缩格式识别和异步 Decompressor 接口；本轮不替换 codec 或改便携更新包策略。

## 实现方案

源码调查显示 KCompressionDevice 在截断时可能返回 0 且 `atEnd()==false`，在解码错误后返回 -1；原循环忽略两者，会一直读取。写入只检查负数，异常后仍可能返回成功，关闭文件前也未检查刷新结果。

采用最小调用层修复：一次分配 4 MiB 缓冲区，使用返回字节数的 read 接口；读取失败、零进展且非正常结尾、短写、刷新失败及 std::exception 均失败；每个已启动的任务退出时关闭输入和输出；取消仍返回失败且发送一次 finished(false)。只把真正完整且成功写出的结果交给现有 UI。部分临时文件仍由原调用方管理，不增加任意解压大小限制。

相比直接更换库，此方案可先建立可比较的正确性基线；相比修改 vendor 解码器，调用层已能区分正常结尾与无进展，改动更小。若测试揭示 codec 内部缺陷，单独记录，不静默放宽测试。

使用 Python 标准库离线生成的小型独立压缩夹具，C++ 测试运行时不需要 Python 或系统压缩工具。覆盖三种格式的空流、含中文／NUL／CRLF 的有效数据、超过 4 MiB 的输出、截断和校验损坏；使用实际 QFile 测试替身保留落盘行为，仅在 writeData 边界制造短写、异常和写错误。真正的缓冲刷新失败使用原生 `/dev/full` 验证，没有该设备的平台仅跳过此项。另测预先取消和写入过程中的取消，完成信号、关闭和返回值保持一致。

这是 P13 首轮，不代表 ZIP／7z／tar、恶意归档路径、大尺寸策略或新库性能已完成。继续运行原便携包测试；本地 master 中文提交，不推送，不增加平台验证要求。
