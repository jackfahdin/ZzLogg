# 搜索提交线程协助执行实验

延续固定 CPU／TBB 预算对照，用户已确认继续验证提交线程协助执行。目标是验证在后台名额有限时，利用已有提交线程是否改善搜索耗时，并保留重正则退化作为否决条件；本轮不改变产品默认行为。

## 实现方案

采用显式 `--candidate assist`：仍用 Qt 匹配器和原 limiter，上限仍是匹配节点数的三倍；提交失败后调用现有图的 `wait_for_all()`，让提交线程协助完成已接纳任务，再重试。它可能把流水线变成小批次，收益和退化都必须测量。增加线程预算已被上一轮排除为产品改动；自建任务队列会扩大并发、异常和生命周期维护成本，本轮不采用。

实验策略只在 `ZZLOGG_EXPERIMENTAL_SEARCH` 编译副本中生效，沿用原异常排空／取消机制。诊断记录协助模式搜索数、因容量不足进入图等待次数、提交线程实际执行的图回调数；最后一次正常 join 的回调也计入后者，不将其误称为容量等待期间的匹配数。

保留默认轮询和显式通知模式；实验支持全局预算 1／2／3。测试真实子进程、完整结果、取消、重复搜索、追加搜索，以及六种故障的准确注入和清理。runner 对 assist profile 检查实际模式与零轮询／零通知等待，不允许命名为 assist 却测了其他路径。

固定 CPU 0／2／4、既有 8 个 Android 合成场景、chunk 1024、同二进制。assist 与 wake 各自对照 Qt，并保留 Qt／Qt 控制，预算 1／2／3，每组四轮、顺反交错。计时与诊断分开；原独立 oracle 校验所有结果。不新增依赖，不调整系统权限，不追加 Windows 测试。

实现细节和取舍由本轮执行者确定：先测队列满即协助的最小策略，不加按查询内容或名额阈值的规则。即使部分场景更快，也不直接升级为产品默认。
